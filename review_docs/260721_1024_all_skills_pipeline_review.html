P-3. Stage 8 산출물 명칭 충돌 [MED]

core-engineering Stage 8 출력은 verification_plan.md, 그러나 Stage 8 전담 스킬 eval-planner의 출력은 evaluation_plan.md. verification_plan.md는 생산자 없는 고아 산출물이 됨 (eval-planner의 validate 스크립트도 evaluation_plan만 검사). uf-designer의 UF Block "Verification Plan" 필드와 용어도 겹쳐 3중 혼선.

P-4. auditor → eval 배선 부재 [HIGH]

README는 "auditor 3종이 eval-planner에 도메인 지표를 공급"한다고 선언하나: ① 연결이 각 auditor의 references/README_kr.md 개념 화살표로만 존재, SKILL.md 본문은 eval-planner/runner 무언급, ② gpu·sim은 eval-planner가 아니라 eval-runner를 지목(불일치), ③ auditor 산출(reports/…)을 eval-planner Inputs가 열거하지 않음 — 배출구와 흡입구가 연결 안 됨. 사람이 수동으로 옮겨야 동작.

P-5. 실험 실행 주체 공백 [HIGH — 신규 스킬 후보 ①]

P-6. proposal_skills 핸드오프 단절 [HIGH]

조사 에이전트 검증 결과(파일 인용 기준): ① 섹션 스킬 5종이 상위 산출물(_proposal_prep_*.md, _kpi_benchmark_*.md)을 파일로 읽으라는 지시 0건 — 대화 맥락 의존이라 단독 호출·세션 단절 시 분석 유실, ② prep 출력 파일명이 SKILL.md와 skill-io-map.md에서 상이(proposal_prep_* vs RFP_analysis.md) → 자동 생성 매뉴얼이 존재하지 않는 파일명 안내, ③ overview 3항 KPI 공급원이 prep·kpi-benchmark·사용자 재질문 3중 — 스킬들이 강조하는 "수치 일관성"과 정면 충돌, ④ 합성 RFP가 경고문만으로 무검증 전파, ⑤ 장별 pptx를 최종 제안서로 병합하는 단계 부재, ⑥ 저장 위치 3종(/mnt/proposal/, [작업폴더]/, 루트) 혼재 + 다과제 파일 충돌 가능 명명.

P-7. 제안서 ↔ 엔지니어링 두 세계 단절 [MED — 신규 스킬 후보 ②]
