# 프로젝트 맥락과 에이전트 설정

기존 설정을 읽고 사용자 요청에 필요한 부분만 병합한다. 현재 유효한 저장소 지침이나 상세 파이프라인 manifest를 일반 시작 템플릿으로 덮어쓰지 않는다.

## 확인과 작성

1. 기존 에이전트 설정, README, 실제 프로젝트 규칙, 빌드·런타임 설정과 정본을 살핀다. Python은 사용 중일 때만 기존 실행기를 찾고, 확인되지 않은 필수 환경만 질문한다.
2. 요청된 에이전트의 파일만 생성·갱신한다. 여러 제품을 요청하면 공통 규칙은 링크로 공유하고 각 파일의 제품별 지침·사용자 편집을 보존한다.
3. 실제 GLOBAL_RULES.md가 있으면 해당 범위의 참조를 넣고 PROJECT_RULES.md가 있으면 연결한다. 규칙 파일이 없다는 사실만으로 독립적인 작업을 막거나 전체 설계를 시작하지 않는다.
4. 목적·실제 입력·정본·실행/검사 명령·사용자 제약을 짧게 기록한다. 없는 문서나 시험을 존재하는 것처럼 나열하지 않는다.
5. 인증은 환경 변수 이름 또는 승인된 저장 위치만 참조한다. API 키 값을 질문하거나 설정·로그·보고서에 복제하지 않는다.
6. 파일·링크·환경 명령의 실제 존재와 요청 범위만 확인하고 변경을 보고한다. 실행하지 않은 검사나 API 호출을 통과로 적지 않는다.

## 넣을 조정 지침

- 메인이 요청 해석·태스크 분해·공유 결정·통합·검증을 책임진다.
- 작은 일은 직접 처리하고, 독립적인 작업만 명확한 입력·출력·쓰기 범위·완료 기준으로 위임한다.
- 같은 파일의 writer는 하나이며 공용 정본·로그·대장은 메인 또는 지정 소유자가 병합한다. 동시 worker 수는 현재 런타임 한도 안에서 정한다.
- worker의 PASS만 믿지 않고 실제 결과·검사를 확인한다. 필수 기준이 실패하면 의존 태스크를 보류하고 독립 작업은 계속한다.
- 긴 작업은 현재 요청·완료한 일·결정·검증·다음 동작을 작은 상태 기록에 남겨 재개한다. 모든 메시지를 저장하거나 사용자 요청 없이 새 채팅을 만드는 것을 기본값으로 삼지 않는다.
- 일반 작업은 lightweight다. 프로젝트가 명시한 tracked 또는 기존 필수 규약일 때만 해당 로그·대장 규약을 적용한다.

## 시작 틀

# Agent configuration
- Shared guidance: <실제로 존재하는 공통 지침>
- Project context: <실제 프로젝트 규칙·정본>
- Environment: <발견한 실행기·빌드·필수 검사>
- Main/worker coordination: <요청 분해·고유 쓰기 범위·통합 기준>
- Resume: <긴 작업에 필요한 상태 기록 위치만>

이 틀을 채우기 위해 불필요한 파일·질문·미확정 경로를 만들지 않는다. 전체 엔지니어링 파이프라인이 필요할 때는 해당 프로젝트의 실제 manifest를 연결한다.
