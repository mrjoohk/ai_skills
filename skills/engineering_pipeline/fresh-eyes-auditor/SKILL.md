# Fresh-Eyes Auditor — 무맥락 에이전트 기반 인식론적 감사 (v3)

작업을 만든 세션 에이전트는 자기 작업 검증에 확증 편향을 가진다. 이 스킬은 **대화 맥락이 없는 새 에이전트**를
스폰하여 산출물을 파일만으로 감사하게 하고, 본 에이전트는 그 발견을 **인용 검증(트리아지)** 한 뒤에만 채택한다.
**자문(advisory) 전용** — 코드·설계를 수정하지 않는다. 단, 발견의 대장(ledger) 기록은 수정이 아니라 감사의 완결 조건이다.

```
[0 범위 확정] → [0.5 기계 검사 선행] → [1 무맥락 에이전트 스폰]
→ [2 트리아지(U-게이트·인용·해명·실질성·재발 대조)] → [3 자문 리포트 + 대장 갱신]

Delta 모드(선택한 변경 검토): [D0 변경분] → [D1 필요한 관점 배정] → [D2 보고 파일] (+ D3 겹치기)
→ [D4 처분표] → [D5 재발 대조] → (고친 뒤) [D6 고침 확인 | 새 코드면 D1]
```

## Step 0 — 범위 확정

"지금까지"는 대화가 아니라 **파일 집합**으로 정의한다:

| 상황 | 검토 모드 |
|---|---|
| 사용자가 파일/폴더 지정 | 지정된 것만 |
| 설계 문서 존재 (`rd/*.md`, requirements.md/uf.md 등) | **Mode A**: ① 설계 문서 자체 감사 + ② (코드 있으면) 설계↔코드 비교 |
| 설계 문서 없음 | **Mode B**: 소스 코드(src/, tests/)만 감사 |

매니페스트에는 실제 경로·검토 기준점·범위를 지정한다. 범위가 크면 메인이 위험과 의존성으로 우선순위를 나누고 검토 범위·제외를 보고한다. 사용자 판단이 필요한 범위 변경만 질문한다.

## Step 0.5 — 기계 검사 선행 (가능하면 반드시)

대상 프로젝트에 설정된 관련 `tools/graph_checks.py` 검사가 있으면 필요한 범위로 실행한다. 없고 프로젝트가 원하면 본 스킬의
`scripts/graph_checks.py`(범용 엔진)를 복사해 쓸 수 있다 — 설정은 `assets/checks_config.template.json` 참고.

- 기계가 잡는 클래스(미사용 선언, 개수 불일치, 인용 실재, enum↔계약 범위)는 스크립트 전담 —
  LLM 감사자는 **판단형 결함**(모호함·억지·환각·논리 모순)에 집중시킨다.
- 기계 검사 위반은 LLM 발견과 구별한다. 프로젝트가 대장을 사용하면 메인이 등록·병합한다. 대장 등록만으로 완료나 품질 통과를 선언하지 않는다.
- 기계 검사 **결과를 스폰 프롬프트에 넣지 않는다**(오염 방지).

## Step 1 — 무맥락 에이전트 스폰

현재 런타임의 하위 에이전트 기능으로 **새** 검토 컨텍스트를 만든다. 기능이 없으면 메인이 비독립 검토로 수행하고 그 한계를 밝힌다. 별도 채팅 생성은 사용자 요청이 있을 때만 한다.

**오염 방지 (위반 시 감사 무효)** — 프롬프트에 넣을 수 있는 것: 파일 경로 매니페스트, 루브릭, 출력 형식,
웹 검증 정책, 검토 모드. 넣을 수 없는 것: 세션 요약·결론·의도·기대 결과·과거 감사 리포트·기계 검사 결과.

스폰 프롬프트는 **`reference/spawn_prompt_template.md`를 그대로 사용**한다(대괄호만 치환).
루브릭 4축·심각도 기준표·출력 형식이 모두 그 안에 있다 — 임의 변형 금지(회차 간 드리프트 방지).

## Step 2 — 트리아지 (본 에이전트, 검증자의 환각 방어)

발견마다 순서대로 (세부 프로토콜과 판례: `reference/triage_protocol.md`):

| 순서 | 검사 | 실패 시 |
|---|---|---|
| ⓪ | **U-의존 게이트**: 판정이 미해소 UNVERIFIABLE(열람 불가 원본)에 의존하는가 | **채택 금지** — 심각도 불문 UNVERIFIABLE로 이동, 사용자 확인 요청 |
| ① | 인용 실재: file:line 직접 Read하여 원문 대조 | REJECTED-MISQUOTE |
| ② | 기재된 해명: 파일 내 판단 근거가 지적을 해명하는가 | REJECTED-JUSTIFIED |
| ③ | 실질성: 수정 시 실제 개선되는가 | REJECTED-TRIVIAL |
| — | 모두 통과 | ACCEPTED |

**재발 대조 (필수 — 생략하면 감사 미완)**: `graph/edges.csv`(있으면 우선) 또는 직전 리포트와 대조해
전 ACCEPTED에 RECURRING/NEW, 해소 확인분에 RESOLVED 태그. 대조표 없는 리포트는 미완성.

## Step 3 — 자문 리포트 + 대장 갱신

`review_docs/YYMMDD_HHMM_fresh_eyes_audit.md` 생성 — **골격은 `assets/report_template.md`를 사용**
(필수 섹션: 기계 검사 요약, 이전 감사/대장 대조표, ACCEPTED/REJECTED/UNVERIFIABLE, 후속 라우팅).
작성 예시는 `examples/example_audit_report.md`.

**대장 갱신(있으면 의무)**: ACCEPTED 신규를 open으로 등록, RESOLVED 상태 전이 기록 —
스키마는 `reference/ledger_schema.md`. worker는 findings를 반환하고 메인 또는 지정된 한 명만 대장을 갱신한다. 대장을 사용하지 않는 프로젝트에 새 대장을 일괄 요구하지 않는다.
CRITICAL ACCEPTED 존재 시 "후속 단계 진행 전 해소 권고"(차단 아님). 프로젝트에 파일 로그 규칙이 있으면 준수.

## Delta 모드 — 범위를 정한 변경 검토

선택한 변경분의 범위·기준점·검토 예산을 먼저 정한다. 필요한 관점을 가용 슬롯 안에서 배정하고, 같은 대상을 새 근거 없이 반복 감사하지 않는다. 독립 검토 입력은 고정하고 변경 시 메인이 기준점을 갱신한다.

| 단계 | 할 일 |
|---|---|
| D0 변경분 | 변경 diff·새 파일 경로와, 바뀐 동작을 보여 줄 실행·시험 명령. 기계 검사(0.5)를 먼저 |
| D1 관점 배정 | `reference/delta_prompt_template.md`와 `reference/delta_lenses.md`에서 필요한 관점만 선택한다. 위험·독립성·실제 런타임 용량에 따라 검토자를 정하고, 관점 수를 필수 인원수로 해석하지 않는다. |
| D2 예산·보고 파일 | 검토자마다 약 15분·도구 40회, 탐침 폴더 따로(그 밖은 읽기 전용). 끝내기 전에 보고를 `<증거 폴더>/delta_review/round<n>_<관점>.md` 로 쓰게 한다(프로젝트 규약이 없으면 `review_docs/`). 트리아지는 **그 파일**로 한다 — 대화 출력은 맥락 압축 때 사라진다 |
| D3 독립 작업 계속 | 검토 입력을 고정한 뒤 메인은 미위임 작업이나 통합을 진행한다. 검토 중인 정본을 바꿔야 하면 검토자에게 변경된 기준점을 전달한다. |
| D4 처분표 | 모든 지적과 **'결함 아님'이라 적힌 설계 메모까지** `round<n>_disposition.md`(`assets/disposition_template.md`)에 한 줄씩 — 처분 FIXED / DEFERRED / ACCEPTED-AS-DESIGN / REJECTED-… 와 근거·시험·대장 ID. ACCEPTED-AS-DESIGN 은 실제 대표 데이터로 돌려 본 수치를 근거로 적는다(말로만 받아들이지 않는다) |
| D5 재발 대조 | 다음 회차를 띄우기 전에 앞 회차 처분표(특히 DEFERRED·ACCEPTED-AS-DESIGN)와 새 변경을 대조한다. 새 지적이 앞 회차 항목과 같은 영역이면 RECURRING — 대장 notes 에 앞 회차 ID |
| D6 고침 확인 | 고친 것만 확인할 때는 **새** 검토자에게 지적 목록 + 고친 diff 만 준다(템플릿의 '고침 확인' 꼴). 독립 감사가 아니므로 보고·처분표에 '고침 확인(비독립)'. 고친 범위 밖의 변경이 생기면 그 추가 diff만 위험·검토 예산 안에서 배정한다. 전체 D1을 자동 반복하지 않고 남은 한계를 보고한다 |

## Rules

1. 스폰 프롬프트에 세션 해석·과거 리포트·기계 검사 결과 주입 금지 — 경로+루브릭+형식만.
2. 인용 없는 발견은 트리아지 진입 전 자동 기각.
3. **U-의존 발견은 해소 전 채택 금지** — 심각도 불문 (트리아지 ⓪).
4. UNVERIFIABLE은 결함으로 집계하지 않는다.
5. **재발 대조와 대장 갱신은 감사의 완결 조건이다.**
6. 심각도는 템플릿의 기준표로만 판정 — 감사자·회차 간 드리프트 금지.
7. 코드·설계 수정 금지 — 검토자와 수정자 분리, 라우팅만. (대장·리포트 기록은 수정이 아니다)
8. 자문 전용: BLOCKED 발령 없음.
9. 하위 에이전트 기능이 없으면 메인의 비독립 검토로 진행하고 한계를 보고한다. 별도 채팅을 임의 생성하지 않는다.
10. Delta 모드 D6(고침 확인)만 규칙 1의 예외 — 지적 목록·고친 diff 를 줄 수 있고, 결과는 '비독립'으로 표시한다.
11. 검토 보고와 처분표는 파일로 남긴다 — 대화 출력만으로 처분하지 않는다.
12. '결함 아님' 설계 메모도 처분 대상이다 — ACCEPTED-AS-DESIGN 은 실제 데이터 근거 필수.
