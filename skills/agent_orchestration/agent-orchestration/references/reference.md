# 태스크·역할·핸드오프 계약

분해의 단위는 에이전트 인원수가 아니라 독립적으로 완료·검증할 수 있는 일이다. 역할 파일과 계획 파일은 장기 재개·다자 조정·사용자 요청에 유용할 때 사용한다. 짧은 위임은 같은 계약을 메시지에 담으면 된다.

## 최소 계약

목표 / 실제 입력과 기준점 / 선행 조건 / 출력 또는 반환 / 읽기·쓰기 범위 / 완료·검증 기준 / 기존 승인·제약을 전달한다. 탐색·검토는 read-only가 기본이고 구현은 고유 범위를 지정한다. 파일이 공유되는 런타임에서도 사적 대화 맥락이 자동 공유된다고 가정하지 않는다.

공유 파일은 단일 writer가 소유한다. worker가 같은 정본을 만들 필요가 있으면 worker별 조각을 반환하고 소유자가 병합한다. domain_metrics.md, 전역 요청 ID, 로그, 대장도 같은 원칙이다.

## 역할 선택 예

| 필요 | 배분 |
|---|---|
| 작은 문구·설정 수정 | 메인 직접, 관련 확인만 |
| 독립 모듈 구현 둘 | 고유 파일로 worker를 나누고 메인이 통합 |
| 조사 후 문서 작성 | 조사 worker와 메인 집필의 독립 작업만 중첩 |
| 중요한 계약 변경 | 구현과 검토 역할을 분리하고 수락 기준 대조 |
| 입력 부족 | 메인이 근거 탐색·필수 질문을 묶고 독립 태스크만 계속 |

Architect·Builder·Verifier를 모두 배정할 필요는 없다. 엔지니어링 1~8단계 전체가 필요한 경우만 engineering-manifest.md를 적용한다. 단계별 실제 산출물과 프로젝트 경로를 재사용하고 완료된 설계를 다시 만들지 않는다.

## 실행과 전달

agent-executor는 기존 파일 형식의 role/task_prompt/inputs/outputs/dependencies/acceptance_criteria/skills_to_use와 추가 write_scope를 소비할 수 있다. Execution Groups가 있는 기존 계획도 필수 입력의 수락 조건을 검사한 뒤 실행한다. 고정 그룹 장벽 때문에 준비된 독립 태스크를 불필요하게 기다리게 하지 않는다.

반환은 status, outputs, summary, checks, findings/blockers를 포함한다. 엔지니어링 파이프라인이 RESULT_JSON의 passed/findings를 요구하면 해당 어댑터 계약을 추가 적용한다. 일반 메시지 위임에 stdout 접두사나 불필요한 보고서 파일을 일괄 요구하지 않는다.

도구 매핑은 현재 환경에서 확인한다. 예를 들어 생성·메시지·대기 API가 제공되면 사용하되 특정 제품의 Agent 도구 이름이나 여러 호출을 한 응답에 넣는 방식이 모든 환경에서 동작한다고 가정하지 않는다.
