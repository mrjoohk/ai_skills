# 실행 계약과 상태

## 입력

agents/orchestration_plan.md와 역할 파일은 선택형 지속 기록이다. 대화로 받은 작업 계약도 사용할 수 있다. 목표·입력·수정 범위·의존성·완료 기준을 확정하면 실행을 시작할 수 있다.

공유 workspace 접근, private context 상속, worker 메시지, 파일 격리는 런타임마다 다르다. 실제 기능을 확인하고 필요한 맥락을 전달한다. 한 worker의 결과 메시지를 다른 worker에게 전달할 때도 필요한 내용과 근거만 보낸다.

## 의존성과 소유권

- ready: 필수 선행 입력이 검증되어 시작 가능한 태스크.
- running: 한 소유자가 맡아 수행 중.
- COMPLETE: 태스크 수락 기준을 충족했고 메인이 결과를 확인.
- PARTIAL: 일부 결과가 있지만 필수 기준 미달.
- BLOCKED: 범위 안의 작업을 막는 필수 정보·권한·외부 상태가 있음.
- FAILED: 시도한 작업이나 검증이 실패.

worker의 자기 보고는 메인 확인 전까지 잠정 상태다. 수락되지 않은 필수 입력에 의존하는 태스크만 보류한다. worker 전체 상태가 PARTIAL/BLOCKED/FAILED여도 메인이 별도로 검증·수락한 독립 부분 결과는 사용할 수 있다. 독립 태스크는 계속할 수 있다.

같은 정본·통합 설정·로그·ID·대장에는 단일 writer를 둔다. 검토자는 기준점이 고정된 입력을 읽는다. 구현이 바뀌면 main이 검토 범위를 갱신한다. 수정도 한 검토를 독립 승인으로 표현하지 않는다.

## 결과 최소 형식

status / outputs / summary / checks / findings / blockers.
checks에는 실제 명령·결과와 미수행 한계를 구분한다. 출력 파일 존재는 수락 기준의 일부일 뿐이다.

전체 engineering manifest의 RESULT_JSON passed/findings처럼 기계 계약이 있는 실행만 그 형태로 반환한다. 일반 위임은 메시지로 충분하다. 장기 작업에는 현재 상태·근거·다음 동작을 작은 인계 기록으로 남긴다.

## 복구와 종료

필수 기준 실패 → 원인 확인 → 수정 또는 재배정 → 영향 받은 검사만 재확인.
불필요한 전체 재실행을 피하고 동일 원인에 대한 반복 시도는 중단한다. 검토·재시도의 범위와 예산은 위험·진전에 맞춰 main이 정한다.

완료는 전체 요청과 통합 기준 충족 여부로 판단한다. 미해결을 ledger에 등록하거나 모든 worker가 종료했다는 사실만으로 완료가 되지 않는다.
