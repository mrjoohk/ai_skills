# Project Summarizer

읽는 사람이 프로젝트의 흐름과 선택 이유를 빠르게 파악할 수 있도록 사실을 압축한다. 특정 프로젝트 경로·로그 형식·규칙 파일을 요구하지 않는다.

## 수집과 갱신

1. 사용자 지정 대상 요약본을 먼저 읽는다. 경로가 없으면 작업공간의 `project_summary.md`를 기본값으로 사용한다. 사용자가 요청한 별도 파일명·폴더·출력 형식을 우선한다.
2. 현재 대화와 사용자가 제공한 설계·작업 기록·검증 보고·산출물을 읽는다. 추가 문맥이 필요하면 관련 작업공간 파일을 제한적으로 탐색한다. `requirements.md`, `uf.md`, `if_list.md`, `.pipeline/`, JSONL 로그 등은 존재할 경우 사용할 수 있는 예시이며 필수 입력이 아니다. 과거 프로젝트나 관계없는 저장소를 검색 대상으로 확장하지 않는다.
3. 기존 요약은 추가·변경된 사실만 병합한다. 해결된 이슈와 새 결정을 반영하되 변경 이력·근거·사용자의 기존 구성을 보존한다. 사용자 요청이 구조 재편을 포함하면 그 범위에서 정리하고, 일반 갱신에서는 무관한 기존 섹션을 삭제하지 않는다.
4. 새 요약에는 [references/template.md](references/template.md)를 사용한다. 기존 요약에는 필요한 섹션만 대응시킨다. 기술·사업·연구 프로젝트 모두 목적에 맞게 용어를 바꿀 수 있다.

## 내용 기준

- 실제 발생한 사실·검증 결과만 기록하고 계획과 완료를 구별한다. 근거가 부족한 항목은 `(정보 없음 — 추후 보완 필요)`로 남긴다.
- 목적·진행 과정·문제와 영향·해결 방법과 결과·교훈·현재 상태와 다음 단계·출처를 연결한다. 섹션당 5~7개 핵심 항목을 목표로 하되 사용자에게 필요한 세부 정보를 우선한다.
- **핵심 설계 결정(Key Decisions)**에는 선택, 검토·기각한 대안, 이유, 근거를 기록한다. 중요한 결정의 근거를 모르는데 그럴듯한 이유를 만들지 않는다. 결정 기록이 없으면 그 사실을 명시한다.
- 기존 주장과 새 증거가 충돌하면 실제로 확인된 변화와 기준일을 적는다. 기존 검증 성공 수치나 과거 승인을 현재 상태로 재사용하지 않는다.
- 내용 근거와 산출물 링크를 남기고 변경된 섹션에 `<!-- updated: YYYY-MM-DD -->`를 사용할 수 있다.

저장 전 요약과 출처의 완료 상태·수치·미해결 항목을 대조하고, 빈 템플릿 자리표시와 중복을 제거한다. 현재 요청이 허용한 저장은 진행한다. 로그는 요청되거나 대상 프로젝트에 지정된 경우 기록한다. 완료 시 신규/갱신 여부, 바뀐 핵심 항목, 파일 링크와 미확정 사항을 보고한다.
